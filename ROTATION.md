# Rotation Patterns

## Dynamic secrets (the default here)

Database credentials generated by Vault's `database` secrets engine rotate themselves: every app start requests a fresh lease, and every lease has a TTL (`default_ttl=1h` in `vault/init.sh`). No rotation job is needed — the credential simply stops being valid, and Vault drops the corresponding Postgres role on expiry or explicit revocation:

```bash
vault lease revoke -prefix database/creds/app-readwrite
```

This is the preferred pattern for anything Vault can generate credentials for (databases, cloud IAM, PKI certs) — rotation is a property of the lease, not a cron job you have to remember to run.

## Static secrets (things Vault can't generate)

Some secrets — a third-party SaaS API key, a webhook signing secret — can't be dynamically issued because Vault doesn't control the downstream system. For these:

1. Store the current value in Vault's KV engine (`secret/app/config` in this demo).
2. Rotate on a schedule (e.g., quarterly, or per your compliance requirement) via a script that:
   - calls the vendor's API to issue a new key
   - writes the new value to Vault (`vault kv put`)
   - triggers app instances to re-read it (Vault Agent template + `SIGHUP`, or just a rolling restart)
   - revokes the old key at the vendor once the rollout is confirmed
3. Record the rotation in whatever audit trail your org uses — KV version history in Vault (`vault kv get -version=N`) gives you the "when did this change" half for free.

## Access review

Because every credential issued flows through Vault, `vault audit` logs give a complete record of which app instance requested which lease and when — useful for incident response ("was this leaked credential ever actually used") without needing per-service custom logging.
